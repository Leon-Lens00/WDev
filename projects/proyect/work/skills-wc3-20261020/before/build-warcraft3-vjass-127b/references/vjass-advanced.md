# Advanced vJASS and JassHelper constructs

## `keyword` forward declarations

Use `private keyword A` or `public keyword A` when a vJASS symbol defined later in the same visibility domain must be recognized earlier, especially for mutually referencing structs.

```jass
library Tree
    private keyword Parent

    private struct Child
        Parent parent
    endstruct

    private struct Parent
        Child first
    endstruct
endlibrary
```

Decision sequence for “type not found”:

1. If defined later in the same scope/library, evaluate `keyword` with matching visibility.
2. If defined by another library, verify `requires`/`optional` and public API.
3. If generated by a textmacro, inspect expansion, invocation order, name, and visibility.
4. Otherwise fix the typo, missing source, or earlier compiler error.

`keyword` does not install a library, declare a plain JASS function, or repair a failed textmacro.

## Normal structs

A normal struct uses JassHelper-generated indexed storage and allocation infrastructure. Define clear construction and teardown. Make every persistent handle field's ownership explicit. Avoid a single global spell state when instances can overlap.

## `extends Parent`

Treat vJASS inheritance as JassHelper pseudo-inheritance, not Java/C++ inheritance. Audit:

- parent allocator and custom `create` methods;
- destructor/onDestroy chain;
- `stub`, `super`, `typeid`, and `getType()` behavior;
- generated names and visibility inside libraries;
- compiler-fork compatibility.

Prefer composition or modules when only code reuse is needed. Keep inheritance shallow and intentional.

## `extends array`

An array struct is indexed storage controlled externally or by a custom allocator. It does not automatically promise normal `.create()`, `.allocate()`, `.destroy()`, or `.deallocate()` behavior.

Good uses:

- player data indexed by `GetPlayerId`;
- unit data indexed by the authorized UnitIndexer;
- a reviewed custom allocator;
- dense system-owned indices.

Audit index 0, bounds, double release, stale references, cleanup before reuse, and index ownership. Reject inheriting a normal child from an array struct by default.

## Classic array and struct limits

The local 1.27b `common.j` declares `JASS_MAX_ARRAY_SIZE = 8192`. Treat that value as the exclusive upper bound, not as a valid index or as a promise of 8192 struct instances.

The installed JassHelper manual documents:

- 8191 values as the normal JASS array storage limit;
- 8190 concurrent instances per normal struct type because struct index `0` is null;
- `floor(8190 / memberSize)` instances for a vJASS dynamic array member of fixed size.

For normal structs and reviewed custom allocators:

- reserve index `0` explicitly;
- guard overflow before incrementing or writing;
- document whether the high boundary is storage or a sentinel/free-list head;
- never hardcode `8190`, `8191`, or `8192` without naming the relevant capacity and ownership rule;
- test exhaustion, release, reuse, stale references, and double release in debug builds.

JassHelper can synthesize larger storage through multiple arrays and function calls, but that changes access cost and compiler dependence. Prefer hashtables or deliberately partitioned storage when sparse or larger capacity is required; record the performance and lifecycle tradeoff.

## Modules and initialization

`implement` injects a module into a struct. A module `onInit`, struct `onInit`, library initializer, and ordinary initialization can run at different stages. Record both compilation dependencies and runtime readiness; do not assume `requires` solves every initializer priority issue.

## Interfaces, stubs, delegates, and operators

- `interface`: use for a stable behavioral contract; verify implementation and dispatch cost/semantics in the installed compiler.
- `stub`: use only when override/dispatch is actually required; inspect generated trigger evaluation if relevant.
- `delegate`: use to forward an API deliberately; document ownership and null/dead delegate behavior.
- `operator`: keep semantics unsurprising; distinguish read and write operators; avoid hiding expensive work.
- `readonly`: use for public observation with controlled writes; verify generated access rules.
- `thistype`: use for the current struct type, especially constructors and modules; it is compile-time substitution, not a runtime type.
- `super`: use only with a valid parent relationship and verified method semantics.

## Textmacros and static conditionals

Textmacros generate source before later phases. When generated symbols are missing, inspect the first compiler error and expanded/preprocessed output before adding dependencies. Keep macro parameters and generated names explicit. Use `static if` only with conditions supported by the installed JassHelper.

## Hooks and external directives

Treat `hook`, `//! external`, ObjectMerger, and other tool directives as toolchain dependencies. Record the executable, patch, side effects, generated objects, and reproducible build command. Never assume a map can rebuild because the final `war3map.j` compiles.
